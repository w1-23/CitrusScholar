# 8043 账号删除、会话清空与运维续清

## 账号删除和日志分类

账号删除先关闭新工作准入，再等待请求引用、排队轮次及控制器执行进入已确认状态。处理中、停止请求已送出、含未知副作用，均不等于已终止。确认后以数字账号 ID 清除队列正文、终态证据、序列、任务和工具回执、文件引用及库文件。对于未带账号 ID 的旧回执，只有已核验的所属会话或该会话内的精确任务关联才可用于清理。不按用户名、模糊日志匹配或文件名猜归属。账号删除后的同名注册会分配不同的数字 ID，不继承旧任务。保存不含账号正文的安全事件以及阻止旧账号重新准入的状态。

| 分类 | 处理 |
| --- | --- |
| 账号业务数据 | 删除使用中的账号范围记录。受其他边界托管的不可识别旧行、备份、SQLite WAL 或磁盘残留不能以导出结果为空认作销毁。 |
| 受管逐任务 TXT | 账号删除期间，只有 `logs/turns/<UTC 日期>/<根任务 ID>.txt` 能由所属会话和持久任务精确验证时才移除。归属冲突时保留并要求核对。 |
| 当日/历史汇总 TXT 和其他历史归档 TXT | 可能含业务文本。由数据和日志所有者按获准的留置、保留期限及精确清单处置。账号删除不扫描这些归档。 |
| 原始 business/agent/diag 及轮替日志 | 不修改原件。生成新导出时只按真实任务 ID 关联其中有限的诊断数值、状态或级别，不重用历史正文或客户端请求 ID。 |
| 最小账号安全审计 | 按安全事件保留策略保存事件类型、时间、匿名化前的内部账号 ID 和经审核的工单编号等最小字段。严禁将用户名、问答、路径或 claim/lease 凭据复制到工单或诊断输出。 |

新 TXT 导出要求账号库可验证，排除已关闭删除准入或不存在的账号，并在原子发布前再次验证。若另一进程在生成期间关闭账号，整份未完成导出不发布，重新运行后才能看到更新后的范围。运营人员主动运行正常的 `--today` 或 `--date` 汇总时，会按既有约定刷新对应的汇总输出，哪怕当日剩余范围为空。这不等于批量处理历史归档。

## 仅清空会话历史

用户的「清空」删除会话消息、引用账本及会话短期记忆，并阻止旧任务从可见历史、队列列表、任务列表及会话任务提示回填。它不删除账号文件库、执行回执、原始诊断或其他会话。已知任务 ID 的状态、事件和操作结果仍可供其已授权的所有者显式诊断，对账时也可使用；发现和历史列表不会再次展示该任务。清空时若检测到正在运行、等待确认停止或未结算的工作，会返回冲突，不删历史或撤除未完成工作所需的附件保护。

## 本地、人工核验后的续清

仅具备目标运行态写权限的可信运维身份可以执行下面的操作。先确认命令使用目标运行态的 `CITRUSQA_PROJECT_ROOT`，再从本地 CLI 查询指定内部 ID。不要以“claim 很旧”“PID 不存在”或服务已重启单独证明旧写入已经整体停止。

1. `python scripts/manage_account.py deletion-status --user-id ID` 查看不可变账号 ID 对应的待删除状态、参考 PID、遗留工作引用数、当前核对指纹。保留原始运维记录，不复制账号资料。
2. 在获授权的事故处置流程，核对目标运行态的服务/容器实例、原清理进程及其所有相关子进程或 Worker 的独立停止证据。留置证据只记入获准的运维工单。不确定，或仍有引用/未核验执行时，停止续清，走独立的进程或执行对账流程。此 CLI 不自动清除工作引用、跳过运行态/执行护栏或接管在线写入。
3. 仅证据充分且工单有授权时运行 `python scripts/manage_account.py resume-deletion --user-id ID --snapshot FINGERPRINT --incident OPS-123 --confirmed-writer-stopped`。新领取 claim 与核对写入是一笔账号库事务。指纹不匹配则不更改状态。恢复过程任何不能确认的步骤均保持账号停用，审批后可重新核对并续清。
4. 复核账号已不可登录、没有剩余待删状态，核对审计事件 `account_deletion_resumed_local` 和 `account_deletion_completed`。使用只读命令 `python scripts/manage_account.py deletion-status --check-pending` 做运维检查，仅输出待删账号与 claim 总数。返回码 0 代表清空，1 代表存在待清理账号，2 代表无法读取。告警与人工核验不触发抢占。

## 历史审计正文与诊断归档维护

管理端的请求审计按一年窗口返回运行元数据。网页搜索范围为当前账号名、会话 ID 和请求 ID。旧问答及未经验证的工具字段保持隐藏。需要处置已存内容时，在明确批准的运行目录内执行独立维护。该维护覆盖指定 `admin_audit.sqlite3` 的全部旧问答以及旧版本的附件、工具和检索 JSON，包括孤立账号的旧行。它保留审计记录、时间、任务关联和当前版本已规范化的元数据。原始 business/agent/diag 日志继续按各自策略管理。

1. 按批准的工单核对数据保留和留置范围。要纳入归档 TXT 时，准备 JSON 数组，每项含归档根目录内的相对 `path` 与准确的 `sha256`。分别核对目标目录、文件内容和工单授权。汇总、逐任务或其他归档仅处理清单列明的文件；正常导出不触发历史维护。
2. 从源目录用 `python 04_scripts/purge_8043_history.py --runtime /approved/runtime --incident OPS-123` 查看范围。要核验归档，追加 `--archive-root /approved/archives --manifest /approved/list.json`。默认只读，输出数量和作用域快照，不输出旧问答或归档内容。
3. 运维独立确认目标库和归档的所有读写进程已停止。使用相同参数追加 `--apply --snapshot <fingerprint> --confirmed-writers-stopped`。作用域变化会拒绝写入。维护在审计数据库记录工单、阶段、作用域摘要和数量。SQL 清理启用 SQLite 安全删除，检查点截断 WAL，并重整与验证数据库。归档操作核对文件描述符和路径身份，按精确清单移除文件。
4. 如运行中断，检查该工单最近阶段，重新做只读核验并用新快照续跑。程序只在领用同一工单和同一归档身份的移除记录后承认文件已缺失。数据库、归档和回执分阶段持久化。备份、快照、镜像、底层介质及其副本仍由数据所有者按另行批准的政策处置。
